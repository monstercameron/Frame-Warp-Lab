# Project working agreement

## Purpose and scope

Frame Warp Lab is an experimental native Windows renderer investigating presentation pacing, asynchronous reprojection and frame generation. The initial graphics API is Direct3D 12, the host language is C++20, shaders use HLSL, and builds use CMake. Research claims are hypotheses until measured on the target system. Preserve the research and test-scene documents as the project evolves.

The central research objective is the **combined** use of frame generation and asynchronous warp/reprojection to investigate whether they can deliver perfectly paced frames at the monitor's upper refresh bound with minimal image degradation and low latency. Single-technique modes are controls that help isolate results, not substitutes for this objective. Test at the verified upper refresh bound of the target monitor and record the active mode, actual observed refresh and whether the target was reached. Never silently lower the target or claim a result when the upper bound, combined integration or display timing cannot be verified; report the limitation. Verify vendor SDK compatibility before combining presentation paths.

## Engineering

- Prefer small, cohesive components with clear ownership. Keep platform/window handling, rendering, presentation, simulation, shaders and telemetry in distinct modules as they grow. Avoid premature frameworks and unnecessary dependencies.
- Use RAII for OS handles and COM objects. Make resource lifetimes, GPU synchronization, queue ownership, frame IDs and timestamp units explicit. Check API failures and report actionable errors.
- Never access a GPU resource while it is being written or reused without the required synchronization. Keep queues bounded; do not hide waits or silently accumulate stale frames. Treat resize, shutdown, device removal and missing optional features as explicit states.
- Keep frame generation and reprojection optional, distinguish rendered, generated and displayed frames, and retain a working baseline. Do not claim compatibility with an SDK, architecture or device without checking actual binaries and runtime capability.
- Isolate vendor SDK integrations behind narrow interfaces. Follow their license and redistribution terms. Do not copy third-party GPL code into this project without an explicit license decision.
- Do not add code comments. Code must document itself through clear, precise names, small cohesive functions, explicit types and straightforward control flow. Variable, function, type and module names must make their purpose clear; avoid cryptic abbreviations. If code is difficult to read, refine its structure and naming until it is clear rather than explaining it in a comment. Record architecture, non-obvious invariants and graphics API requirements in project documentation, and enforce invariants in code where practical. Use consistent formatting and C++20 standard facilities. Avoid clever abstractions that obscure timing and resource ownership. Keep shaders and source files organized by responsibility.
- Keep generated build output and local captures out of source control. Never commit credentials or machine-specific secrets.

## Versioning and commits

- Make frequent, small, coherent Git commits as work progresses. Commit each completed, independently understandable idea or meaningful change promptly, after appropriate focused verification; avoid mixing unrelated changes. Do not commit broken intermediate work merely to increase frequency.
- Use Semantic Versioning (`MAJOR.MINOR.PATCH`), with the version in `CMakeLists.txt` as the source of truth. Increment MAJOR for incompatible public interface or behavior changes, MINOR for backward-compatible features or significant new capabilities, and PATCH for backward-compatible fixes and smaller improvements. During initial 0.x development, continue to use these distinctions intentionally; a 0.x MINOR increment may also signal a breaking change, which must be called out explicitly.
- Update the version with each committed meaningful change or idea and include the resulting version in its commit message, for example `v0.2.0 feat: add frame timing capture` or `v0.2.1 fix: handle device removal`. Use a concise type and description; identify breaking changes in the message. Documentation-only changes should normally increment PATCH so their commits also carry a concrete version.
- Never rewrite existing commits or discard uncommitted user changes without explicit authorization. Inspect the working tree before staging and commit only relevant files. Record what was tested and any material limitations in the handoff; do not imply that a commit or version validates an experimental performance claim.

## Measurement and verification

- Log the configuration, frame IDs, timestamp units, source-frame age and fallback reasons. Report scene rate, display cadence, latency and image quality separately. A present call or FPS counter is not proof of actual display timing or input-to-photon latency.
- Reproduce comparisons with controlled paths, workloads and recorded settings. Expose artifacts and missed deadlines; do not silently smooth over failures.
- Build and run appropriate focused checks after changes. Test resize, shutdown and error handling when affected. State clearly what was and was not tested, especially on Windows ARM64 and optional NVIDIA features.
- Update README and research notes when setup, architecture, verified capabilities or experimental conclusions change. Do not present a prototype as a guaranteed refresh-rate solution.

## Runtime observability and agent CLI

Build strong observability and full agent access into each subsystem as it is implemented. The documented CLI is a first-class interface to the application: an agent must be able to discover, inspect, diagnose, configure and operate every applicable feature and resource without relying on screenshots, manual UI interaction, or guesses. Provide full create, read, update and delete (CRUD) operations for each applicable resource, as well as actions needed for lifecycle and control. Some runtime facts and physical resources are inherently read-only or have different lifecycle semantics; expose their meaningful operations and explicitly report unsupported operations and reasons rather than pretending they support CRUD. Expose meaningful runtime dimensions, including when a dimension is unavailable or not yet implemented; do not invent data or conflate estimates with measurements.

- Provide discoverable commands and help, stable machine-readable JSON output, meaningful exit codes, and concise human-readable output where useful. Document command syntax, units, defaults, examples, and compatibility when commands change. The CLI must be able to identify and target the intended running instance.
- Expose application and build identity; process and instance status; adapter, driver, device and feature support; window, monitor, resolution, refresh and presentation configuration; active modes and settings; simulation, input, render, GPU, warp, frame-generation and display timings when actually measurable; frame IDs, queue depth, frames in flight, source age, missed deadlines and fallback reasons; resource and memory usage where available; and errors, warnings and device-loss state. Clearly distinguish requested settings from observed state, CPU timestamps from GPU timestamps, and present calls from observed display events. Label estimates, unavailable metrics, and their collection methods.
- Use structured, timestamped logs with severity, subsystem, event name, instance and relevant frame or correlation IDs. Include units and useful context for errors and state transitions. Keep logs useful for both agents and people; avoid unbounded per-frame spam. Make verbosity and high-frequency tracing configurable, and use bounded buffers, rotation or retention limits so observability cannot exhaust disk or memory.
- Support inspection of current state and recent events as well as bounded, opt-in capture of detailed frame traces for a specified interval or frame count. Diagnostic commands must avoid blocking the render/presentation path or perturbing timing more than necessary; document and measure capture overhead when it matters.
- Expose applicable CRUD and lifecycle controls for scenes and their objects, cameras, render and presentation settings, workloads, experiment configurations and runs, telemetry captures, and other resources as those features are built. Include creation, listing, inspection, modification, deletion, start/stop, and reset where meaningful. Commands must return stable identifiers and the resulting state or an actionable error, support deterministic scripting, and report validation failures without partially applying a change unless documented. Where full atomicity is impossible, report exactly what changed.
- Ensure every capability available through a GUI or other interface is also accessible through the CLI, including configuration, diagnostics, experiment execution and results retrieval. Add the CLI operation and machine-readable representation as part of the feature, not in a later phase. Expose schema or equivalent discoverable help for resources, supported fields, units, allowable operations and versioned output. Clearly report permissions, unsupported functionality and unavailable backends.
- Make read-only inspection safe by default. Clearly distinguish commands that change settings or runtime state, validate inputs, and return the applied value or an actionable error. Do not expose unrestricted remote control or a network listener by default; use a local, appropriately scoped communication mechanism and avoid logging secrets.
- Design telemetry and CLI interfaces alongside features, not as an afterthought. Add focused checks for command output, error handling, unavailable data and trace bounds when those interfaces are implemented. Keep a documented inventory of implemented versus planned commands and metrics; a requirement in this file is not evidence that the capability already exists.
